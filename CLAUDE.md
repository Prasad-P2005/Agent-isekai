## Commands

```bash
python -m venv .venv && .venv/Scripts/pip install -e ".[dev]"     # first time; on Linux/macOS use .venv/bin/
.venv/Scripts/python -m isekai                                    # http://localhost:8000
.venv/Scripts/python -m pytest                                    # all tests, no network needed
.venv/Scripts/python -m pytest tests/test_rules.py::test_guild_quest_flow   # one test
node --test "tests/client/*.test.mjs"                             # the simulation, terrain, culling and shared data (Node 21+, no install)
node --no-warnings tools/boot_check.mjs                           # starts the whole client on a stand-in page, to catch what would stop it loading
docker compose up --build
```

Changelog emails live in `emails/`: write an entry in `emails/changelogs/`, run `python tools/make_changelog.py <entry>.json`, and send the `.html` and `.txt` it writes as a Resend broadcast to the segment `Isekai Realms Newsletter`, from `noreply@system.solithix.com`. It has to be a broadcast, because Resend fills in the unsubscribe link only there. The title (`emails/title.png`) and the pictures (`gallery/`) load from GitHub, so push them before sending.

`make_changelog.py` also writes `content/news.json` from the newest entries, which is the What's New page: `emails/` is not in the Docker image. Run it with no entry to refresh only that.

There is no linter, formatter or JS build step. If a map or terrain change is deliberate, refresh the stored copy with `python tests/test_world.py` and update `WORLD_HASH` in `tests/client/terrain.test.mjs`.

The client is plain ES modules served as-is from `client/`, with three.js vendored in `client/vendor/` and resolved by the import map in `index.html` (and again in `lookbook.html`). `FreshFiles` in `isekai/app.py` serves them `no-cache`, because a browser left to guess keeps old modules next to new ones. The interface's sprites in `client/img/ui/` and `client/css/icons.css` are drawn by `python tools/make_ui_art.py` (standard library only), so change the art there and commit what it writes. The fonts are vendored in `client/vendor/fonts/`.

Items and recipes are generated: change the tier and kind tables in `tools/make_items.py`, run it, and commit `content/items.json` and `content/recipes.json`. `node tools/item_sheets.mjs` draws every item into `docs/items/`, `node tools/hand_sheets.mjs` draws what the hero holds into `docs/hand/`, and `node tools/cave_designs.mjs [what]` builds caves in memory and renders them into `docs/caves/`, including the walk measure below. None of them needs a browser.

Settings are environment variables read once in `isekai/config.py`, and the README lists them all.

What the player chooses lives in the browser, not the server: `core/settings.js` (every option, and the graphics presets) and `core/bindings.js` (keys). The pages in `ui/settings.js` are drawn from those lists, so a new option is one line there plus whoever reads it, and an option nothing reads does not get added. `ui/look.js` applies the ones that change the page itself: interface size, what is on the HUD, the font, colour help and full screen. Anything that reacts listens for `settings:changed`, which names the keys that moved. The simulation asks `held('forward')`, never for a key code.

Debugging: `http://localhost:8000/lookbook.html` renders every character; in the browser console, `isekai.teleport('name')`, `isekai.G`, `isekai.ents`.

## Architecture

The game is called Crown Reborn. `isekai` in the code (the package, `ISEKAI_*`, the `isekai-*` storage keys, `window.isekai`) is the old working name, left alone on purpose: changing a storage key would wipe every player's settings.

One FastAPI process, one `Game` (`isekai/core/game.py`), one open `World` (`isekai/core/state.py`) out of however many are saved. Single player, no auth.

**The split between server and client is the key thing to understand.** The server owns state and rules: player profile, laws, economy, story, residents. The client owns the simulation: terrain, physics, combat, creature AI. They meet over HTTP:

- The client reports what happened (`/api/event`, `/crime`, `/report`, `/blocks`, `/context`) and applies the `state_payload` it gets back. Effects it must carry out, such as spawning golems, come back as a dict for `applyEffects` in `client/js/sim/effects.js`.
- The server cannot push. Anything it originates goes through `World.push()` into the feed, which the client polls every 2.5 s (`startSync`, `handleFeed` in `net/sync.js`).
- Terrain never crosses the wire. The server sends the seed, lands, building layouts and streets, and `client/js/sim/terrain.js` turns them into blocks deterministically. Anything that changes noise offsets, RNG draw order or structure generation reshapes existing worlds. Only the player's changes are stored: `sim/edits.js` tracks them, and `/api/blocks` saves them in `World.block_edits` together with the inventory, so the two cannot disagree.
- **The client owns the bag**, for the same reason it owns the world's blocks: mining, durability and crafting cannot wait for a round trip. `Player.bag` is 36 slots of `{id, n, dur}`, the first nine the hotbar, and `Player.worn` holds armour and the off hand. It goes to the server with `/api/blocks`, `/talk` and `/service` as a `pack`. The server never writes to it: anything it gives or takes is a parcel (`systems/bag.py`), applied once by `applyParcels` and acknowledged in the same request as the new bag, so a crash can neither lose one nor double it. `Player.blocks` is only a summary for the story, favors and attunement. `Player.weapon`, `tool`, `armor`, `potions`, `mana_potions` and `loot` are read by nothing but old save steps.
- **What lies in the world** is the client's too. `sim/drops.js` holds it, in Minecraft's numbers: what a block gives and what a creature leaves pops out and lands, and the hero takes it by walking over it. Loot is rolled on the client from `loot`, `meat` and `drops` (a list of `[item, chance, least, most]`) in `creatures.json`, so a body's drop lands where it fell without a round trip. Nothing the bag has no room for is lost: it stays on the ground, or lands there. It goes to the server in the same `pack` as the bag and the stations (`packReport` in `net/sync.js`), so nothing is saved in two places or in none. Dying drops nothing, on purpose.

**Server layers.** `api/` only reads requests and calls `core/commands.py`, which is everything the player can do. Commands use `systems/` (laws, shop, guild, story, storyteller, dialogue, favors, chronicle, people), which know nothing about HTTP. `world/` lays out the map, `world/genesis.py` draws a new world from its seed, and `persistence/` reads, writes and upgrades saves.

**One game clock.** `World.clock` counts seconds played. It only advances in `Game.tick`, and only while `Game.playing()`, which needs a recent `/api/context` report saying `playing: true`. Merely polling the feed does not count. Cooldowns, festivals, raids, world events, idle narration, favors and the guild board all run on it, so a pause pauses them all. Use `World.after()` for anything due later: timers are saved, so a restart cannot lose them. Never use `time.time()` or `asyncio.sleep` for gameplay.

**Client layers.** `core/` is shared basics, `sim/` is the game itself, `view/` draws it, `net/` talks to the server and `ui/` is the page. The rule that keeps this working: `sim/` imports only `core/` and `sim/`, never `three`, the DOM, `view/`, `ui/` or `net/`. It announces what happened with `emit` from `core/events.js`, and the others listen. That is why `tests/client/sim.test.mjs` can run the whole simulation in Node. Each entity's meshes live on `e.view`, which only `view/bodies.js` touches. The simulation advances in fixed 1/60 s steps (`core/loop.js`, `sim/world.js`).

**The way in.** `ui/title.js` runs the boot screen, the main menu and the loading bar. Entering or leaving a world starts the page again behind a fade (`ui/session.js`), with `?play` on the address to go straight in, because the world lives in the state of dozens of modules and only a fresh page is sure to hold none of the last one. So the server opens the slot first, and the page that loads plays whatever is open. While `G.phase` is `title`, `view/vista.js` flies round the capital of the open world, or of a sample from `/api/vista` if there is none, through `titleFrame` in `main.js`. It takes liberties with the camera, `G.dayTime` and the hero's position because nothing it does outlives the page, and any failure stops it and leaves the painting up, so scenery can never cost someone the menu. New World, Worlds, How to Play, What's New and the settings are pages of the book opened over the menu (`ui/worlds.js`, `ui/extras.js`), and closing one on the title emits `title:back` instead of going back to a game.

**Who is alive.** `sim/beings.js` holds the list, `sim/entities.js` moves bodies and lands blows, `sim/brains.js` decides what each one wants, `sim/spawning.js` what arrives and `sim/lifetime.js` what leaves. A brain only sets `e.mx`, `e.mz`, `e.pace` and `e.aim`, and `brain` in `creatures.json` picks which one. Creatures notice with `senses`: seeing needs a clear line, hearing only closeness, and what they notice they remember for a while.

**Finding the way** is `sim/paths.js`, two tools for two questions. Everything hunting the hero reads one shared flow field, a flood outward from them done a little each step, so twenty wolves cost the same as one, and running away is walking up it. Errands of one's own (a baker going home) ask for an A* path, one a step, and a walk too long to find at once comes back as a stretch and is continued. A wall is only jumped if it is a step (`ledgeAhead`); otherwise it stops a body and the brain chooses again.

**Spawning** follows Minecraft and reads `content/spawns.json`. Every few seconds each category under its cap picks a spot in a ring round the hero, out of their sight, and if it suits a rule from that land's table a pack appears there. Only creatures near the hero count against a cap. Monsters need a natural floor (`wildFloor`, so never indoors), no lamp nearby and, unless a rule says `"light": "any"`, darkness. Cave spawns happen only while the hero is underground, and the surface rests until they come back up. Things the story or the law send go through `spawnNear`, which waits and retries if there is nowhere to stand, so an event the server announced does not silently fail.

**A body that cannot be built costs that one body.** `view/bodies.js` catches the failure and leaves the being with no `e.view`, and everything there skips such a being. Thrown instead, it would stop every frame from being drawn while the simulation and the HUD went on, which looks like a frozen screen and nothing else. `tools/boot_check.mjs` builds every creature, because spawning is random and this only shows when someone walks into one. Colours in `creatures.json` are numbers by the time anything reads them: `core/content.js` converts them.

**Creature lifetimes.** `sim/lifetime.js` decides when a creature leaves the world: at once past 128 blocks; at random once it has been out of range and idle for 20 seconds; sooner by daylight if it is `nocturnal`. Unlike Minecraft, nothing soft-despawns while `inView`. Golems and hunters off duty walk away and go when unseen. Beings that live in structures carry a `home` hint, handed back to `hintQueue` when they leave, so they return with the player and keep their wounds, and a slain garrison fills again after a while. A named foe left behind comes after the hero again (`foe:lost`). Residents are spawned and removed by `updateResidents` instead, where the slots follow the hero: someone who matters takes a place from whoever got one first, or the middle of a city would stay empty. A witness with a report pending never leaves, or running away would silence them. `sacred` creatures (the stones, the Voice of the Deep) have no AI and cannot be hurt, so the story cannot lose them.

**The god cannot touch the world.** This is the game's premise. There is no LLM: the god is `systems/storyteller.py`, which runs on the game clock and picks from options the engine offers.

- `direct()` runs on every tick: scheduled raids, easing war prices, decrees, idle narration and `_watch`, which is what she notices (low health, dusk, the end of a blood moon).
- `omen()` runs from a saved timer and sets off one event from `allowed_events()`, and a prayer for help (`answer_prayer`) goes through the same list, so the god can only ever lean on a rule. **She is a director**: every event is in `THREATS` or `RELIEF`, and `_weight` picks by `strain()`, how hard things have been lately, so someone on the ropes gets a caravan, someone cruising gets a horde, and a threat is followed by a quiet spell.
- `narrate()` is the god's voice, and routine lines give way if she spoke a moment ago. What she says follows what happened: `mourn()` chooses by how the hero fell, and `noticed_find()` speaks when a pool `tell:found:<item>` exists.
- `decree()` adds a law from `decrees` in `content/laws.json` once its `when` is met.
- **Every Law has a second line.** `systems/edicts.py`, with the text and numbers in `content/edicts.json`. Writing Laws is her whole power, and a gift always comes with a price. The hero picks one of three she offers, and that is how they choose their own difficulty. A Law held already deepens, so its gift grows and its price does not, and the world holds `most` of them, oldest out first. This is the First Law's twist in miniature, which is why she jokes about it in heaven.
- **The deal** decides which Laws come, and the top of `edicts.py` lays it out. Three cards, each from a different place: one from what the hero does (`Player.deeds`, filled through `edicts.noted`, so a digger hears about digging), one from how they are (`moods`: hurt, broke, wanted, night, war), and one by pure chance, a tier rolled and any Law of it taken, whose odds of something rare climb with `Player.dry`. A Law in `edicts.json` has a `sign`, a `tier`, `moods` and perhaps an `ability` it needs, and the weights are in `pull`. Each card can be written in gold or red (`inks`), a Law Stone adds a fourth card that is not common, and the card says why it came (`why`). The hand is kept in `Player.deal` until a Law is written, so looking again changes nothing, and the hero can ask for other words once per Law (`redraw`). Everything she has ever offered goes in `Player.laws_seen`, which is the book on the Laws page (`codex`, fetched from `/api/rules` when the page opens, because it is too much to send with every feed). A new Law is a new entry and two lines in `edict:<id>`; a new rule also has to be read as `rule('name')` somewhere.
- **Rules.** A Law is multipliers, `effects()` multiplies them with whatever is happening now, and each bends in the one place it is decided. The client reads `rule('name')` from `core/rules.js`, and `G.rules` arrives with every state and feed. `rolled(luck)` turns a rule that is a count into one: 1.5 is one and a coin toss for a second. Rules that are a chance, such as `crit` and `dodge`, are 1 plus the chance. Each realm has an Old Law too (`law` in `content/realms.json`), which only reaches the client, so it can only name client rules. `tests/test_god.py` checks that every rule something sets is read somewhere.
- **Faith** is `systems/faith.py`, the one bar every deed fills, shown on the dock. A full bar is a level: a little health and a `petition`, a Law she owes. Each bar starts part full, the first is close, and `earn` is the only way in. Numbers both sides need are `faith` in `content/world.json`. Dying costs none of it, on purpose. It takes the run of nights (`Player.nights`), and the only other streak is the kill chain, `fervor` in `sim/momentum.js`.
- **Talking to her.** `T` opens prayer anywhere, and `dialogue.pray` answers. The first page is business (guide, aid, an offering, what she owes), and `pray_more` opens the chat, where what she knows (`pray_deeds`, `pray_leaning`, `pray_news`) is always there and three of the small talk are drawn each time, to keep the box short. All of it comes from real numbers, and `pray:self` is told in order, tracked by `Player.god_told`. An offering is what is in the hand, or a thing thrown down within reach of a Law Stone, and `faith.offer` counts one gift in a while so that Faith cannot be bought by the stack. At a Law Stone, `stone_pray` opens prayer with `near: stone`. A night at an inn can bring `storyteller.dream`, which plays as a scene.
- **Sieges** are `systems/siege.py`: a settlement, a timer, a compass mark. The assault spawns when the hero arrives, because only what is near them is simulated, and if nobody comes people die and prices rise. The third Oath brings one to the capital, which the King remembers.
- **Blood moons and falling stars** are events: `World.blood_moon` feeds `effects()` until dawn and `view/sky.js` shows it, and `sim/stars.js` cuts a crater through `setBlock` when the ground has loaded.
- **The story is data.** `content/story.json` holds the chapters, oaths, scenes and beats. A beat names its speaker, what it needs and what it changes, and `systems/story.py` only reads those rules, so a new story conversation is a new beat and needs no code. A scene plays once, in the talk box, from a `scene` feed item. What an ending does to the world beyond flags and fields goes in `_end`. A scene with `auto` plays by itself once its conditions are met, and `siege` on one sends an army. A beat can also name `faith`, `tally` (a count to raise) and `tell` (a pool, chosen by whether she has confessed).
- **The stones.** Eleven souls came before the one at the cairn, and each left an `echo` creature, placed by `place_echoes` and sent to the client as hints with no height, which spawning finds when the ground has loaded. Each is its own speaker (`echo:3`) with a beat `echo_3`. Reading all of them, forgiving her, and carrying the crown to a Law Stone opens the fourth ending, the fifth line, where `_end` and `effects()` free every Law of its price.
- **The First Law is real.** `hurtEntity` refuses to wound anything `warded` (the Demon Lord, the Wyrm) until `player.oathbound`, and only the player can hurt them, so their deaths always reach the server. Their wounds stay on the `home` hint and in `World.boss_hp` and `World.dragon_hp`.
- **There is one dragon.** It sleeps in the hall under the Wyrmcrown, the land whose structure is `dragon_peak`. `crown()` in `sim/land.js` raises the mountain and `carveLair` in `sim/terrain.js` hollows it, by the column, because a hall that wide reaches further than a feature may. `wyrm` in `sim/brains.js` is a small state machine: asleep, wakes, chases, home. Inside and outside are joined by the shaft at the summit, so that is the way it flies between them. `home.grudge` is what it remembers. Nothing else ever makes a dragon: it is in no spawn table, and `nemesis_rises` skips anything `warded`.

**Creative mode** is `Player.creative`, switched on the pause card through `/api/creative` and read with `creative()` from `core/state.js`. Each rule bends in the one place it is decided: `damagePlayer`, flight's cost in `updatePlayer`, `ready` and `spend` for spells, `updateMining` and `placeBlock`, `commitCrime`. `updateEntity` hands brains `free: false`, as it does for a pause, so no brain needs to know the mode exists; only the Wyrm does, because it would otherwise hang in the air. `hurtEntity` does not read it, so the First Law holds. Blocks still go through `setBlock`, so a creative build saves like any other, and the hero's real stock is left alone.

**The land** is worked out in layers, each importing only the ones before it, which is what keeps them free of cycles: `sim/land.js` reads the grid of lands through wandering coordinates and gives each column a height, a biome and blended grass and leaf colours (`columnsOf`, cached per chunk); `sim/roads.js` stamps streets, highways and piers into a per-chunk table; `sim/flora.js` grows things, `sim/structures.js` raises landmarks and each realm's sights (`SIGHTS`), `sim/towns.js` builds settlements; and `sim/terrain.js` assembles a chunk and re-exports the rest. Blends decide height and colour; `zone` decides ground cover, frayed by a few blocks either side of a border; and `rollBiome` picks trees from the blend, so that two realms mingle where they meet. `landOf` is still the plain grid: it says whose land a spot is, for names, settlements and structures.

**The deep** is `sim/caves.js`, which runs inside `genChunk` and is built to what the hero can do: step up one block, fall five unhurt, fall any distance into water. Three kinds of cave add into one field read on a 4 block lattice: colossal halls (a regional mask, with a lens of analytic floor and vault, and pillars), tunnels (Minecraft's 2D spaghetti, in three layers that drift together to meet, so they are near level and flat-floored by construction) and tight 3D threads. A hall's floor has no noise on it, which is what keeps its steps to one block. Near the surface a cave is plain rock and ore, and below `BIOME_TOP` the rock just behind the field is painted by the cave biome. Formations are seeded by the world, not the chunk, so they can be far wider than one. **The Old Ways** are a road network on a loose grid: 3 by 3 timbered corridors, railed trestle bridges where they cross open space, crossings with chests that stock themselves the first time they are opened, ramps to the surface with lamps at their mouths, and rope-ladder shafts wherever a road passes a tunnel. They run on the tunnels' own levels and level out either side of a crossing, or they would come up under its floor. Anything that changes these reshapes every world, and `node tools/cave_designs.mjs walk` and `real` measure how much is reachable on foot, so run them after changing floors, tunnels or roads.

**Throwing** is `tossHeld` and `throwAway` in `sim/drops.js`. G throws one and Ctrl+G the stack, in the world or over a slot in the bag, and what leaves the bag's panel lands in the world: a click outside it throws what the mouse carries, and so does letting go of a stack dragged out. What is thrown takes two seconds before it can be taken back. Creative mode throws copies, marked `copy`, which are never saved and never reach the bag, because its hotbar holds no real things, and a creative hero takes nothing.

**Crafting** is `sim/crafting.js` (recipes), `sim/stations.js` (furnaces, forges and chests, saved in `World.stations` by position, burning out of sight) and `sim/hands.js` (what right click does). Shaped recipes can sit anywhere on a grid and mirror. Recipes unlock with `Player.seen`: a recipe opens once its result, or everything that goes into it apart from sticks, has been held. A tool's class, level and speed are in `items.json`, and a block's `tool` and `level` in `blocks.json`: the right tool divides the time by its speed, and a block above the tool's level takes 3.3 times as long and drops nothing. A block with no `level` gives way to anything, which is on purpose for mana: the story needs it.

**Quest marks** say where the things the hero is after are. `systems/marks.py` builds them from the story (`marks` on a chapter or an oath in `story.json`, which take the same conditions as a beat and name a speaker, a `places` entry or a `hunt`), the guild quest and the favor, and they travel with the objective. Marks that share an `id` are alternatives. `sim/marks.js` follows the person or creature behind a mark and keeps the nearest alternative, and `ui/compass.js` and both maps read that one list, `questMarks()`.

**What people say** is built in `systems/dialogue.py` from the pools in `content/lines/`. Those files merge into one flat table (`LINES`), so pool names are global and the files only organise the writing. `lines.say` takes a line nobody has heard lately (`World.said`), expands `#rule#` from other pools, then fills `{blank}`; `tests/test_lines.py` lists which blanks each pool may use. A person's temperament and life come from the seed and their id (`trait_of`, `life_of`), so they cost nothing to save. Real events go into `World.chronicle` with `chronicle.record` and reach other settlements at walking pace (`known_at`) as `gossip:<kind>` lines. Conversations are topic buttons: each exchange returns the next `topics`, and story beats appear among them.

**Settlements** are built in layers: `world/map.py` places them from the `MAP_ROWS` grid, `world/layouts.py` lays out their streets and gives each building the nearest free lot facing one (`Plan`), `content/jobs.json` declares jobs, `systems/people/roster.py` turns those into residents with seeded RNG, and `world/genesis.py` names everything from `content/names.json`. Someone who dies is replaced in place by `succession.py`, keeping their id, so what a post owes the hero survives and a settlement never fills up with the dead. `replaceSettlement` keeps everyone unchanged standing where they are. On the client only residents near the player exist as entities (`updateResidents` in `sim/people.js`).

## Shared data

`content/*.json` is the single source of truth for what both sides need: world, town and building sizes (`world.json`), realms and how each looks, blocks, creatures, items, services, jobs, laws, guild quests, abilities (with their mana costs) and event names. `spawns.json`, `bestiary.json`, `title.json` (splashes, tips, the guide, credits) and `news.json` (generated, see above) are read only by the client. `difficulty` in `world.json` is a set of rules that `effects()` multiplies in for the life of a world, so it reaches the client the way a Law does. The server loads it in `isekai/content.py` and the client in `client/js/core/content.js`, served from `/content`. Change the data once and both sides follow. `names.json`, `story.json`, `favors.json`, `edicts.json` and `lines/` are read only by the server. `items.json` and `recipes.json` are generated, so see above.

Five things are still code on one side that names data from the other. `tests/client/` checks them, so a mismatch fails a test:

| Data                            | Code it must match                                                   |
| ------------------------------- | -------------------------------------------------------------------- |
| `Building.kind` in `layouts.py` | `BUILD` table in `sim/towns.js`                                      |
| `tex` in `content/blocks.json`  | `PAINT` table in `view/blocktex.js`                                  |
| `jobs` in `content/jobs.json`   | `OUTFITS` in `view/outfits.js`                                       |
| `content/events.json`           | `WORLD_EVENTS` in `sim/worldevents.js`; `run_event` in `storyteller.py` |
| `art`, `pal` in `items.json`    | `SPRITES` in `view/itemsprites.js`, `PALETTES` in `view/itemart.js`  |

Job `work` and `night` values are building kinds, or one of `field`, `gate`, `shore` (`_spot` in `roster.py`). When they are the same, the person lives at their post and can be found at any hour; the middle of the ground floor of a building in `HALLS` has to stay clear for them to stand on.

## Saves

Each world is a file in the save folder, and the file's name is its slot (`persistence/saves.py`). The newest file is the one a restart opens, so opening a world saves it, and a rename puts its time back. New World never touches another slot, and a delete moves the file to `trash/`. `Game.open_slot` is the only way to change which world is open, and a page sends the slot it is playing as `X-World`, so that a tab left open gets a 409 instead of writing its bag and blocks into another world.

`World` is pydantic and saved whole, so new fields need defaults. `load()` returns `None` for an unreadable save, and the game then behaves as if no world exists, but the file is first set aside as `world.unreadable-<time>.json`, so creating a new world cannot destroy it. Changes that need old saves rewritten go in a new step in `STEPS` in `persistence/migrations.py`; `save_version` and new worlds follow automatically.

## Client notes

The interface has two materials: the book (peach paper, for what the player reads and decides) and the slate (mauve stone, for what their hands use: the dock and the bag). Everything in `css/style.css` is a multiple of `--u`, one art pixel, and `--text` and `--title` are multiples of the fonts' own grids, so keep sizes on it or the pixels stop lining up. Sprites are 9-slices used through `border-image` with `image-rendering: pixelated`.

`ui/pointer.js` is the only place that may lock the mouse, release it or show the pause screen: `capture()` returns to the game, `release()` hands the mouse to a menu and `pause()` shows the card. Its header lists Chrome's rules, the one that bites being that releasing Esc counts as pressing it, so a lock taken while Esc is down is dropped at once. Automated tests cannot see that: keys sent over CDP skip the browser's handling.

The bag is a small slate panel with the recipe book and the spells against its right edge, and `ui/inventory.js` holds its mouse handling, which follows Minecraft's with the Mouse Tweaks mod, and acts on the press. Slots are elements made once, and `paint` writes only what differs, so a click rebuilds nothing. Every place a stack can sit is a box in `BOXES`, and a station swaps the crafting corner for its own panel.

A slot in the bag also throws: G over it, and a click or a drag outside the panel. `beside` in `ui/inventory.js` says what counts as outside, and it calls `preventDefault` on the press so that `ui/panels.js` does not take it for a click beside the book.

Menus are pages of one book. `definePage(name, { tab, view, render, leave })` in `ui/panels.js` adds one, `togglePage` opens it, and `render` fills `#pageleft` and `#pageright`, or a layout of its own when `view` names one (the bag and the world map). Conversations are not in the book, on purpose: everyone from a farmer to the god to a scene uses `#talk`, and heaven uses the same `.dialogue` box, low and wide and no more than a third of the screen's height, with one line at a time and the topics as a short two-column list. The camera turns to whoever is speaking. Anything to buy or choose (shops, the guild, the temple, a bounty, the Laws she offers) sits in `#side`, a card at the edge that is as tall as what is on it. `body.talking` hides the HUD behind them. Text from the simulation, the server or the god goes through `rich()` in `ui/art.js`, which swaps its emoji for sprites.

The world is drawn by its own shaders in `view/materials.js`, which all read the one `shared` set of uniforms that `view/sky.js` updates each frame. Colours stay in display space from painted tile to screen, so nothing here passes through tone mapping and the art keeps its colours; only bodies and the hand use three's lights, and `updateSky` keeps those in step. Block art is `view/blocktex.js`: 16 x 16 tiles painted in code, with no DOM or three.js, so the bag's icons and Node can read them too. A block names its tiles with `tex` (one name, or top, side, bottom), and the mesher takes `shape`, `cutout`, `sway`, `tint`, `glow` and `emit` from the same entry. An opaque tile's alpha says what a tint touches, which is how grass greens and the dirt under it does not.

There are two looks in those same shaders, chosen by `setLook`. The base game is as above. With `SHADERS` defined, `view/pipeline.js` takes over the frame: colours go linear and bright, sun and shadow are worked out per pixel, and each frame runs the sun's view (three squares of one depth map, `cascades`, near ones often and far ones rarely), the solid world, contact shadows, water and glass, shafts of light, bloom, then tone mapping and the colour settings. Everything on `LATE_LAYER` is drawn after the solid world, because water reads the finished picture behind it, so a new see-through thing goes through `late()` in `view/scene.js`. `sky.js` feeds linear colours and real light when `shadersActive()`. If a shader will not compile, `renderer.debug.onShaderError` turns shaders off and says so. The base look has no such fallback, so a compile error there is a black world: check those shaders with extra care.

`view/mesher.js` turns a chunk plus `LIGHT_REACH` blocks of its neighbours into faces with nothing but numbers, so that it can run on a worker, and `view/meshtables.js` is what it is told. `view/chunkmesh.js` sends it the work and keeps what comes back. It floods sky and lamp light through the volume, the lamps in red, green and blue from `light` in `blocks.json`, then writes four layers: solid, cut-out, glass and water. A vertex is 24 bytes, laid out at the top of `mesher.js`, and every quad shares one index list, which is why a quad's diagonal is turned by starting from another corner. Evenly lit flat tops are merged into rectangles, so per-block differences (`drift`, a grassy top's turn) are done in the fragment shader. Light is baked into the corners, so a change to a lamp re-meshes chunks that far away (`setBlock`). A block is `OPAQUE` only if it is a whole, solid cube; `DIM` is what light loses going through it, and stairs and slabs block the sky without being opaque, or roofs would leak and neighbouring faces would vanish. Lanterns, fences and the like are boxes in sixteenths in `SHAPES`, while collision stays a whole block unless the block is `passable`, as plants are. `raycast` takes what counts as a hit: plants can be mined but do not block sight.

Water does not dim the sky in the mesher, or a sea bed would go black: each wet face carries how much water stands over it and the shader fades by that. Blocks marked `wet` (kelp, sea grass) are drawn in a cell that still counts as water, so use `wet()`, not `=== WATER`, wherever something asks whether a place is under water.

Drawing only what can be seen is `view/culling.js`, which is Tommo's cave culling, as used by Minecraft and Sodium. The mesher flood-fills each 16 x 16 x 16 section to record which faces reach which, and each frame `walkSight` spreads out from the eye's section. The rule that may not be broken is that culling can draw too much but never hides what is visible, and `tests/client/culling.test.mjs` checks it by casting sight lines through real terrain, so run those after touching any of this. The walk only moves outward along each axis, because a straight line cannot turn back, skips what is out of view, and walks a section again for each new face it is entered by. A mesh is drawn if the walk reached any section it touches, so cave walls show when the eye can see them, from anywhere. What survives becomes `worldGroup.children`, so three.js never walks what is hidden. Chunks are generated on workers too (`sim/chunk.worker.js`, handed in through `useFarm`), and both jobs fall back to the main thread if workers fail, which is how the tests run. Workers cannot use the import map, so nothing `sim/terrain.js` or `view/mesher.js` imports may reach `three`.

Characters are drawn like Minecraft skins: big chunky pixels, an 8 pixel head on a 12 pixel body and 12 pixel legs, shaded by hand-sized clusters of tones, with armour, capes and hair as chunky layers on top. Keep it at that resolution: finer pixels look busy, and flat colours look bad. One size of pixel runs through every model (`PIXEL` in `view/voxel.js`), so a dragon's pixels match a farmer's, and only girls' faces are finer, because cute needs the pixels. Men come in mixed adult builds, every girl is cute (`girlish` in `view/outfits.js`), humans all stand 1.8 tall like the player, and kings wear robes to the floor. `view/voxel.js` is how anything living is built: every face of every box is painted into one texture sheet and rigged into one skinned mesh, so a body costs about two draw calls. `view/paint.js` holds the materials. A paint maps a pixel of a face to a colour or to -1 for a hole, which is how a cape tears and hair gets a hairline; `draw` adds marks like trim. Don't let two surfaces share a plane where they overlap, or they flicker: the head has no front of its own for this reason, and lower limbs are a hair narrower than upper ones. Body materials carry `LIFT`, because the world's light and tone mapping dim a colour to about half of what was painted. Colours are the palette at the top of `view/outfits.js`, which is the one in `tools/make_ui_art.py`. People are in `view/avatar.js`, everything else in `view/creatures.js`, and `view/pose.js` holds the motion as plain functions of a record from `newMotion()`, so the world, the bag, heaven and the lookbook share it. A bone's scale has to be set after `rig.finish()`, or binding cancels it. The player's own arm is `view/hand.js`, and the simulation only announces what it does (`player:struck`, `player:placed`, `fireball:cast`). Where things sit and how they swing is `view/held.js`, which needs neither three.js nor the page, so `tools/hand_sheets.mjs` can draw exactly what the game draws: check art there. `view/itemmesh.js` makes those models into meshes, and `view/drops.js` uses the same ones for what lies on the ground, at Minecraft's sizes: a quarter of a block for a block in its true shape, half for a slab, turning and bobbing, with a heap of up to five for a stack. Each kind is one instanced mesh lit by the same lights as bodies, so its lighting follows the sun in both looks. It follows Minecraft: one blocky arm, and only the thing itself when something is held, with its swing and its way of holding tools. Blocks are the deliberate exception, tilted and turned so that a cube shows its top and two sides. A block in the hand is cut from its tiles in its true shape (`SHAPES` in `view/shapes.js`), what grows is carried as a picture, and an item's sprite is extruded into a slab. `MOTIONS` in `hand.js` gives every weapon and tool its own swing. Swords and greatswords swing in cuts, `cutMotion` in `held.js`: a pure function of how far through the swing it is, which leaves rest and returns to it exactly, with the way back hidden under the view. A cut is a rigid arc round a point below the view, because nothing holds the hilt and a flat sprite has to keep facing the eye. `writeTrail` traces its crescent from those same poses, on a pixel grid fixed to the view, so the mark can only be where the blade went. Only a blow or a swing at the air is a cut: chopping at a block, placing and blocking use the plain swing. The arm has its own camera at a fixed field of view, and is lit by the light where the hero stands. Nothing goes through tone mapping, so a block in the hand matches the world.

Bodies and the camera are drawn between the last two steps of the simulation: `fixedSteps` returns how far it got, `e.last` and `player.lastEye` hold the step before. Walking up a ledge lifts `player.pos` at once and adds the height to `player.stepLag`, which `eye()` subtracts and a spring takes back down, so what the player sees rises smoothly while the physics stays simple.

Sound is `view/sound.js`, made from oscillators and noise with nothing to load, and it only listens to events. Each sound goes through the Effects or Menus channel and then the master. There is no music yet: long soundtracks are coming from outside, so do not synthesise any, and the Music slider arrives with them. Feedback is layered and small: a hit gets a sound, a flash and the sight changing colour, and only a kill gets the camera kick and the hit-stop in `main.js`, or nobody would feel them. Reasons for this and the rest of the loop, with sources, are in `docs/specs/2026-11-01-what-keeps-people-playing.md`. Nothing may use real time, a daily login or anything missable for good: pausing pauses everything.

Keep particles low on anything the player sees often. The fireball is the most used attack, so `view/fireball.js` lists its cube counts at the top: use a few chunky cubes rather than many small ones, and keep those counts down when changing it. `view/spells.js` and `view/fx.js` (block chips, dust, splashes) draw through the same cubes and list their own counts, and `view/ambience.js` keeps each realm's air to one draw call of 72 points.

Fish are `view/fish.js`, three schools in one draw call that exist only in the view, so they cost the simulation nothing.

Spells live in `sim/abilities.js`, and two at a time are in hand: `Player.spells`, on Q and R. A staff in the hand strengthens them. Those that choose their own targets strike only `isFoe`, so that they can never commit a crime for the player, and all damage still goes through `hurtEntity`, so the First Law holds. `Player.max_mana` belongs to the server, like `max_hp`: `systems/magic.py` deepens it, the client reads it through `maxMana()`, and spent mana reaches the server in handfuls as `cast` events.

`client/js/` has no import cycles, so module top level is free to use imports. Keep it that way: dependencies point from `ui/` down through `net/` and `view/` to `sim/` and `core/`. `core/content.js` loads the data with a top-level `await`, which pauses every module that imports it. `lookbook.html` imports `view/avatar.js` and `view/creatures.js` directly and must keep working without the game, so nothing they import may need `core/content.js`.
